### Task 2: Fault Localization using Soot (45%).

In this task, you need to design and implement an effective fault localization algorithm by yourself to locate the injected faults revealed by the provided fault-revealing tests.

The four fault-revealing test suites are provided in `./src/test/fault-revealing-randoop[0,1]` and `./src/test/fault-revealing-evosuite[0,1]`.

The program will fail on some tests of these suites. Note that fault localization requires at least one failing test. You need to use these four given test suites for fault localization.

Through this exercise, you will appreciate that *generated tests containing noises can affect the effectiveness of fault localization*.

#### Requirements

- Instrument CUT using Soot to collect necessary information (e.g., how many times each **statement** (rather than each source line) was executed by the passed and failed test cases, respectively) during the running of tests, and run the **four fault-revealing test suites** we provide to collect the information.
- Implement the classic **Ochiai** fault localization algorithm to compute the fault likelihood of each **statement** and generate a report for fault localization. Please note that we are working at the statement level (i.e., identifying faulty statements rather than faulty lines).
- Localize the faults injected by us based on the spectrum and fix them using one-line patches. Write a brief report to list the found faults and your fixing patches.
- Explore the use of LLMs to assist your fault localization and fixing procedures, and share your usage using a short paragraph.

#### Notes

[This](./reference_a2.pdf) research paper describes the **Ochiai** algorithm and can point you to the original papers of the algorithm.

The report should provide useful information indicating where faults reside in the source code. There are **multiple faults** injected in the subject program, and each of them is **in a single line**. Note that some provided test suites may not reveal all injected faults; however, every fault that you are expected to locate and fix is revealed by at least one of the four provided test suites. We injected no more than 10 faults. The exact number of seeded faults is not to be released. Please locate and fix as many faults as you can. But you will be penalized for reporting statements as faults if they do not contribute to any failure in the four provided test suites.

#### Ranking of Suspicious Statements

The ranking value of a statement with a suspicious score $a$ should be computed as $\frac{N+M+1}{2}$, where N is the number of statements whose suspicious scores are higher than $a$ and M is the number of statements whose suspicious scores are higher than or equal to $a$. For example, if a sequence of suspicious scores is (0.9, 0.8, 0.8, 0.8, 0.8, 0.7), then their rankings are (1, 3, 3, 3, 3, 6), respectively. This is equivalent to assigning tied statements the average of their rank positions.

### Task 3: Test Suite Extension (15%).

You may find that the top-ranked suspicious statements reported by your program are not actual faults. In such circumstances, you may consider enriching the test suite by adding more test cases manually, with the assistance of LLMs. You can design a series of effective prompts (as you did in Assignment 1 Task 3) to achieve the goal. Through this exercise, you will appreciate the approach of collaborative fault localization, i.e., localizing faults through human-machine collaboration.

#### Requirements

- Extend each of the four given test suites to improve the rankings of real faulty statements in Task 2 by adding new tests.
  - You are *prohibited* from deleting tests in the four given test suites. 
  - You may use the same set of newly created tests to extend more than one of the four provided test suites. In other words, you can add the same tests to one or more test suites evosuite/randoop 0/1 provided by us simultaneously.
  - The set of new tests that you create for one test suite must *NOT* contain duplicates (which take the same test input and exercise the same code coverage). In other words, within a single refined test suite, you must not add duplicate tests.
  - We consider the rankings of suspicious statements given by the `Ochiai` ranking function.

#### Submissions

1. The four refined test suites (in Java files). Put them in `./src/test/refined-[randoop|evosuite][0,1]` folder.
2. The spectrum reports of each potential faulty statement running against the refined test suites. In total, you need to submit four reports. Please name each of them in the format `spectrum_fl_ochiai_refined_[randoop|evosuite][0,1].tsv`.
3. A brief extension result report that concisely explains your strategy for test case design and clearly compares the results before and after refinement for each of the four test suites. Store the report in `${PROJECT_ROOT}/src/test/refined-[randoop|evosuite][0,1]` folders accordingly.

#### Grading Scheme:

* *Effectiveness of test cases* (15%). Your grade in this task is related to both your average ranking among all test suites (as mentioned in Task 2) of each injected fault (the ranking value is expected to be *lower*, the better) and the average number of tests you add in each test suite (the *fewer*, the better).

  Your score of each faulty statement `s` is: Score<sub>s</sub> = (15% / N) * (`default average ranking` - `your average ranking`) / (`default average ranking` - `best average ranking among classmates`), where N is the total number of injected faulty statements, and `default average ranking` is the average ranking among all provided test suite of a specific faulty statement.

  Suppose `NT` represents the average number of new tests that you have added to each of the given four test suites. The total grade is given by ΣScore<sub>s</sub> *  (`largest NT among classmates` - `your NT` + 1) / (`largest NT among classmates` - `smallest NT among classmates`)

  **NOTE**: We will run your refined test suites using our fault localization tool with the `Ochiai` ranking function. So your score on Task 3 will not be affected by the correctness of your implementation (which will only be judged in Task 2).


### Task 4: Test-Driven Code Generation (20%).

In the previous tasks, you generated test cases for existing code. In this task, you will explore the opposite direction: generating code from test cases. We realize this with the help of LLMs. Please design effective prompts to drive LLMs to generate code based on the test cases of several methods in the CUT. Then, validate the generated code using different test suites and discuss your findings about the effectiveness of LLMs and the quality of generated code.

#### Requirements

- Select at least 10 methods from `Subject.java` and create a new class that contains these methods. The selected methods must keep their original method signatures (i.e., the method name, input parameters, and return type) unchanged. In other words, you may remove unselected methods from the original CUT, but the new class should remain compilable and preserve any necessary fields, constructors, and helper methods required by the selected methods. Then, use Evosuite to generate test suites for these selected methods in the new CUT.
- Prepare code generation prompts for the selected methods. The prompt should include suitable instructions, the generated test suite, and the signature of each selected method. You can prompt the LLM to generate all methods together in one round of generation, or you can prompt the LLM to generate each method separately in multiple rounds of generation (with according test cases and method signature provided in each round).
- Test the LLM-generated code using the test suite generated by Evosuite. If the LLM-generated code cannot pass the test suite, provide the failing test results and relevant error messages back to the LLM and ask it to refine the generated code. You can iterate this process several times (e.g., 3-5).
- Evaluate the final LLM-generated code by comparing it with the original code in `Subject.java` to analyze its similarities and differences.
- Write a report to discuss your findings. The report should include the following aspects:
  - The prompt that you use to generate code based on test cases;
  - Analysis on the pass rate of the first-round LLM-generated code on the Evosuite-generated test suite;
  - Analysis on the pass rate of the final LLM-generated code after several rounds of refinement on the Evosuite-generated test suite;
  - Analysis on the similarities and differences between the final LLM-generated code and the original code in `Subject.java`;
  - Your insights on the strengths and limitations of LLMs and the Evosuite-generated test cases in test-driven code generation, and suggestions for improving the success rate of test-driven code generation using LLMs.

#### Notes:

- We encourage you to use HKUST OpenWebUI `hkgai-v1`-series models freely available on [HKUST OpenWebUI platform](https://openwebui.hkust.edu.hk/), but other publicly available LLMs are also allowed. Note that please do not use agent services provided by the LLM platforms (e.g., Codex in ChatGPT) to complete this task, as we are actually simulating the iterative process of agentic code generation and refinement based on test results in a clean way, which may help you better understand the strengths and limitations of LLMs in code generation and refinement. 
- For each of the following four aspects, you are encouraged to write 150–300 words and use appropriate tables/figures: (1) the testing result of the first-round LLM-generated code on the test suite; (2) the testing result of the final LLM-generated code after several rounds of refinement on the test suite; (3) the similarities and differences between the final LLM-generated code and the original code in `Subject.java`; (4) the insights on the strengths and limitations of LLMs and the Evosuite-generated test cases in test-driven code generation, and suggestions for improving the success rate of test-driven code generation using LLMs. The report should be concise and informative, and the writing should be your own work (i.e., you should not use LLMs to generate the report text directly, except for quoting specific LLM outputs that you actually used during the process).
